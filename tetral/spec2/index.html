Introduction

Tetral, from the Greek word for “four,” is a scripting language intended to be executed by an interpreter, or virtual machine, and to provide a platform-agnostic execution system. This document will serve as the specification for this language and outline key aspects of its grammar, type system and code execution.

1.Core Principles🔗

Tetral is designed with the following 4 core principles in mind.

Statically Typed
Types must be specified and known at compile-time to allow for execution environments to optimize as much as possible and to provide easy readability for programmers.
Platform-Agnostic
As long as an interpreter exists, it shouldn’t matter how the IR was compiled, it should be possible to execute it.
Explicit Null Control
Values should never be allowed to be null, unless explicitly stated to be otherwise.
Memory Safety
Users of the language should not have to worry about freeing or allocating memory manually, and should not worry about the objects they’re using becoming de-allocated as they’re using them.

Scope

This document defines the Tetral scripting language (Also referred to as TetralScript, or TetralLang) and the Tetral Bytecode format.

Terms, Concepts and Definitions

Source File
A text file containing Tetral source code.
Bytecode / Intermediate Representation (IR)
The compiled representation of Tetral source code. The terms “bytecode,” “IR,” and “intermediate representation” are used interchangeably throughout this document.
Program
A valid Tetral source file or Tetral bytecode file that can be executed by a Tetral execution environment.
Access
To read or modify the value of an object.
Bit
A single binary digit, having a value of either 0 or 1.
Byte
A sequence of 8 bits. The byte is the smallest addressable unit of memory.
Alignment
The requirement that a value of a given type be stored at a memory address that is a multiple of that type’s alignment value.
Padding
Unused space inserted in memory to ensure that a value is stored at a correctly aligned address.
Native
Describes a feature, function, variable, or library implemented in a lower-level language, such as C or C++, rather than in Tetral.
Symbol
An entity that can be referred to by a name. Symbols include, but are not limited to:
  • Functions
  • Structs
  • Enums
  • Classes
  • Local variables
  • Global variables
  • Imported symbols
Namespace
A named scope that groups related symbols. Namespace names are written as a sequence of identifiers delimited by ::.
Simple Name
The name of a symbol as written in a source file, without a namespace prefix.
Fully Qualified Name
The name of a symbol prefixed by its namespace.
Binary Name
The name of a symbol in compiled Tetral IR.
Module
A collection of functions, types, and variables declared within a specific namespace.
Implicit Import
A module that is imported without being explicitly imported by the user. Implicit imports vary by execution environment.
Code unit
An encoded unit of data corresponding to a Unicode encoding.
Code point
A Unicode code point. For more info on codepoints, please see the Unicode Standard.
Character
Unless stated otherwise, this term refers to a code point.

Conformance

Any program able to accept a valid source file or valid bytecode file as input for execution is considered a conforming Tetral execution environment.

Source code validity is defined in the following language section and bytecode file validity is defined in the bytecode format section.

Any use of “shall”, or “must” in this document declares a constraint that must be followed.

Environments

The Tetral language may be executed in one or multiple of several contexts, or execution environments.

Depending on the context of the execution/compilation of a Tetral program, the environments used may differ. For example, an embedded program loading a Tetral source file may first use the Compilation Environment and then the Embedded Environment to execute the code, or only the Embedded Environment if loading a bytecode file.

2.Translation Environment🔗

The translation environment provides only basic support for language features required to evaluate constant expressions and constant functions.

Translation environments only operate on Tetral source files.

3.Standalone Environment🔗

A standalone environment is one where a Tetral file is executed as a fully standalone program with a single defined entry point.

A standalone program’s entry point must be defined as a function with the name main and have one of the following signatures:

  • void main()
  • int32 main()
  • void main(string[] args)
  • int32 main(string[] args)

The standalone environment must also provide full support for the standard library and the importing of external symbols.

Standalone environments must also implicitly import the std and std::strings standard library modules.

4.Embedded Environment🔗

An embedded environment is one in which Tetral programs are executed by a native application which embeds a conforming Tetral execution environment. This environment has no pre-defined entry point, nor any predefined libraries that the environment must implement.

Native-level bindings are not pre-defined for embedded environments are defined by the program embedding the Tetral execution environment.

Data Types

A data type is a specific unit of memory that holds data in a specific layout to represent some piece of information.

This section defines the data types implementations must support and the kinds of data types that can be declared by users of the language. Additional terminology and information may be defined for each data type in its corresponding section.

Each section will also define the following properties for its data type:

  • Whether the data type can be default-initialized. Default initialization determines whether an object of that data type can be initialized without a value being explicitly declared.
  • The data type’s string representation. The string representation of a data type’s value is used in string templating and when concatenating a data type’s value with a string.
  • Whether the data type can be compared with other data types and if so, how that comparison is done. If a data type states is can be compared, then it is considered a comparable type.
  • Which types of values the data type can be equal to and how equality is established.

Data types additionally exist in two categories. The first category is value types. When value types are passed to a callable object or assigned, the value is copied to the destination. Reference types, on the other hand, only pass a reference to the data type’s value.

Data types may be referred to more simply as just types.

5.The Boolean Type🔗

The boolean data type shall be a value data type which represents a false/true state.

The boolean data type must be represented by a single byte in memory. If the byte’s value is 0, then the boolean value is false, otherwise it is true.

Boolean values shall be default-initialized. The default boolean value shall be false.

A boolean value’s string representation shall be either “true” if the value is not false, otherwise it’s string representation shall be “false.”

Boolean values shall be compared only to other boolean values. A boolean value shall be considered “less than” another boolean value if it’s value is false, and the other boolean value is true. A boolean value shall be equal to another boolean value if both hold the same true/false state.

6.The Void Type🔗

The void data type represents a non-existent value. Used for functions/methods which return no value. This data type shall only be used in specifying the return type of callable objects. No variables, properties or class fields shall use the void data type.

The void type’s string representation shall be “void”. Since the void type must not exist as a value, it cannot be compared to another type, nor shall it be possible to establish equality with any value of any type.

6.1.Integral Types🔗

Integral types shall be value types of varying sizes used to represent whole numbers.

Integral types shall be default-initialized. Each integral type’s default value shall be its equivalent of the value 0.

Each integral value’s string representation shall be its numerical value converted to a base-10 string. If the integral value is signed and is negative, the string representation shall be prefixed with a "-".

Integral value comparability and equality Semantics are stated in the next section.

The floating-point types shall be value types which hold a numeric value according to the corresponding IEEE-745 standard format.

Floating point values shall be default-initialized. Each floating point type’s default value shall be that type’s 0 value.

Each floating point type’s string representation is it’s numerical value converted to a base-10 ASCII string.

Arithmetic values shall only be compared to other arithmetic values. An arithmetic value shall be considered less than another arithmetic value if and only if the numeric value it represents is lesser than the other value’s represented numeric value.

Arithmetic value equality shall only be established between any two arithmetic values. An arithmetic value shall be equal to another if it’s represented numeric value is equal to the other arithmetic value’s represented numeric value.

7.Array Types🔗

Array types shall be a kind of reference type which hold a sequential list of a specific data type.

Each unit of data contained in an array shall be referred to as an “element,” and the amount of items the array holds shall be called its “length.”

The data type contained by an array type shall be referred to as its component type.

Arrays shall exist in two separate kinds: mutable and immutable. Elements in an immutable array cannot be changed, while in a mutable array, they can.

Regardless of an array’s mutability kind, an array’s length shall be fixed and cannot be modified after creation.

Array types shall be default-initialized. An array type’s default value shall be an empty array, an array with length 0.

The string representation of an array value shall be a string prefixed with "[" followed by the string representation of each of its elements, delimited by ", " and then followed with "]". The string representation of an empty array shall be "[]".

Equality between array values shall only be established between two array values of the same component type. If the lengths of two arrays differ, they shall not be equal, then if every element of one array is equal to the corresponding element in another array, the arrays shall be equal.

Array values shall only be compared if both arrays are of the same, comparable type. The first N elements of both arrays are compared, with N being the length of the smaller array. The first element that is greater than or less than the corresponding element in another array determines how the arrays compare. If no element is greater than or less than a corresponding element in another array, then the array with the smaller capacity is lesser. If both arrays are of the same length, the arrays are equal.

8.The String Type🔗

The String type shall be a reference type which holds a sequential list of UTF-8 code units.

The string type shall be immutable, none of its elements can be changed. The amount of UTF-8 code units stored in a string shall be called its “length.”

Array and string types collectively constitute the “indexable” types. This means these types can be accessed with the index operator. ([])

The string type shall be default-initialized. Its default value shall be an empty string, a string with length 0.

The string representation of a string shall be the string itself.

String value equality shall only be established between two string values. Likewise, strings shall only be compared with other strings. The Semantics for both string equality and comparability is the same as Array equality and comparability.

9.Struct Types🔗

Struct types shall be a kind of value type, which are made up of “properties,” each of which shall have a name and a pre-set data type, determined by the user.

Structs shall not hold any properties that directly or indirectly reference the struct itself.

A struct type may be default-initialized. If each property’s type in a struct can be default-initialized, then so can the struct. Otherwise, if all properties which cannot default-initialized have a default value specified, then the struct shall be default-initialized. Otherwise, if a struct contains properties which are not of a default-initialized type and do not have a specified default value, the struct shall not be default-initialized.

The string representation of a struct shall be a string prefixed with "{" followed by the name and value of each property. The name of a property shall be separated from its value with a " = “ sequence and each pair of property name and value delimited with ”, “. The string shall finally be suffixed with a ”}" sequence.

Struct equality shall only be established between two struct values of the same struct type. If every property’s value in a struct is equal to another, then the struct values shall be equal.

Struct values shall not be comparable.

For example this struct:

struct A {
uint32 a = 0
float64 b = 0
}

Defines two properties:

  • The first property is named ‘a’ with a 32-bit unsigned integer as its data type.
  • The second property is named ‘b’ with a 64-bit floating point number as its data type.

Both properties are initialized to a default value of 0.

10.Enum Types🔗

Enum types shall be a kind of value type that declare a list of named constant integer values. Each constant value will be referred to as an enum-constant.

The underlying value of an enum constant shall be referred to as its “ordinal” value.

Enum constants may have a value explicitly declared, but this is not required. If an enum constant’s value is not declared explicitly, then it’s value shall be the value of the previous enum constant plus 1. Enum constants may declare the same value as another enum constant in the same enum type.

The maximum possible ordinal value an enum constant may hold is 2147483647 and the smallest possible value is -2147483648.

An enum type may be default-initialized, if there exists an enum constant in that enum type with the ordinal value 0. Otherwise, it shall not be default-initialized.

The string representation of an enum constant shall be the string representation of the ordinal value of the enum constant.

Enum values shall only be compared to other enum values of the same enum type. An enum value shall be less than another enum value if it’s ordinal value is less than another enum’s ordinal value.

Enum value equality shall only be established with enum values of the same enum type. An enum value shall only be equal to another enum value if it’s ordinal value is identical to another enum value’s ordinal value.

For example the enum declaration:

enum E {
CONST_A = 1,
CONST_B,
CONST_C = 0,
CONST_D,
}

In this enum declaration:

  • The enum constant CONST_A has the explicit ordinal value of 1.
  • The enum constant CONST_B has the implicit ordinal value of 2.
  • The enum constant CONST_C has the explicit ordinal value of 0.
  • The enum constant CONST_D has the implicit ordinal value of 1.

11.Variant Types🔗

Variant types shall be a kind of value type which define a list of variants the variant type itself can take the form of.

Variant types will be referred to as variant types, while each declared variant will be referred to as a variant of the variant type, or more simply as just variant.

Each variant of a variant type shall declare 0 or more properties, each of which must have a name and a pre-set data type.

The index of a variant in a variant type is referred to as its “ordinal” value.

Variant types can hold type parameters.

Variant types shall be default-initialized if the variant with ordinal 0 has no properties.

The string representation of a variant shall be a string prefixed with the name of the variant type of the value and then followed by a string representation of each of its properties in the same manner as the string representation of structs.

Variant values shall not be comparable.

Establishing equality of variant type values shall only be possible with variant type values of the same variant type. Equality shall first depend on the variant type values having identical ordinal values. If the variant declares any properties, all property values must be equal between the variant values. If no properties were specified, then the variant type values shall only be equal if their ordinal values are identical.

For example the variant declaration:

variant Optional<T> {
Empty(),
Present(T value),
}

Has two variant types:

  • The first is named Empty and has no properties, thus this variant can be default-initialized.
  • The second is named Present has one property, the type parameter property.

12.Interface Types🔗

An interface type shall be a kind of reference type, but not a type which can itself be instantiated.

Interfaces shall declare 0 or more methods which must be defined by any class wishing to implement the interface.

Implementing an interface shall mean declaring a class as being an implementer of an interface type and defining a function body for each of the methods the interface declares.

Interfaces may hold type parameters.

Interface types shall not be default-initialized.

Interface equality and comparability Semantics shall be the same as those for class types.

13.Class Types🔗

Class types shall be a kind of reference type which define class members. Class members are either constructors, methods or fields.

Constructors are functions which shall be invoked upon the creation of a class type’s value. Constructs may, like functions and methods, require certain arguments to correctly initialize the class instance.

Methods shall be functions that exist within the namespace of a class. Methods shall also be divided into two separate types: static and non-static. Static methods belong to the class, while non-static methods belong to a class instance. Methods inside classes and interfaces shall have access to the this keyword that shall refer to the instance of the class the method belongs to. For static methods, the keyword shall not be available.

Fields shall be the properties that belong either to class instances, or for static fields, to the class itself. Non-static Fields shall be subject to the same padding and alignment Semantics as struct properties. Non-static fields may be referred to as “instance fields” and static fields referred to as “class members.”

Classes may extend one other class and can implement as many non-conflicting interfaces as described in the limits section (See 15. Limits.) Non-conflicting shall mean that none of the implemented interfaces have themselves declared methods, or inherited methods from another extended interface, whose function signatures are in conflict. Two function signatures are in conflict if their argument types and name are the same, but not their return types.

Class extension shall mean the extending class gains access to all its public and protected members. Classes can also override any non-const methods of its extended class.

Unless specified otherwise, the term extend will be used for classes implementing interface as well.

Classes and interfaces will be referred to collectively as object types.

An object type extended by another object type is referred to as the parent of the extending object type. An object type extending another object type is referred to as the child type of the extended object type.

A type which directly or indirectly extends another type (by way of its parent extending the type, for example) is referred to as a derived object type of the extended object type. Vice versa, the term super will be used for an object type which is extended indirectly or directly by another object type.

Class types may hold type parameters.

Functions, and methods on object types are collectively referred to as callable objects, or just callables.

Classes may override any non-static methods of their super types that are not marked as const. Overriding shall mean that all calls to the super type’s method instead go to the derived object type’s method.

Class types shall not be default-initialized.

The string representation of a class type value shall be a string prefixed with the name of the class type followed by the string representation of each of its properties, regardless of access modifier, in the same fashion as the string representation of structs.

Class type values shall not be comparable.

Class type value equality shall only be established between class values of identical class types or between class types where one is a derived type of the other. If two class values are not of the same class type, they shall not be equal. Otherwise, the value of each instance field must be equal to the corresponding instance field.

13.1.Function Types🔗

A function type shall be a kind of reference type which outlines the argument types and returned type of a callable object.

Function types shall not be instantiated nor shall they be default-initialized.

The string representation of a function type shall be a string prefixed "(", followed by a ", “-delimited list of the names of each argument’s data type. The string is then suffixed with ”) -> “ followed by the name of the returned type.

Function types shall not be comparable to any value of any type.

Function value equality shall be possible to establish with other function values of the same function signature. Function type values shall only be equal if they refer to the same function.

13.2.Nullables🔗

A nullable type shall be a value type which marks another type as nullable, meaning its value may or may not exist.

The value existence state of a nullable value is referred to as it’s presence state. And the type a nullable type is being used on shall be referred to as the “nulled type.”

Nullable values shall be default-initialized. Nullable values shall be initialized to a value with a false presence state by default.

The string representation of a nullable shall be either the string “null” if the presence state of the nullable value is false, or the string representation of the nulled type’s value, if it’s value is present.

Nullable values shall not be comparable to any value of any type.

Nullable value equality shall only be established between nullable values of the same nulled type, or between a nullable value and a non-nullable value of the same nulled type. If both nullable values have a false presence state, they shall be equal. Otherwise, the nullable value’s nulled type’s values must be equal in order to establish equality.

18.8.Power (POW) Expression🔗

18.8.1.Syntax🔗

18.8.2.Constraints🔗
  1. Both operands must be of a compatible arithmetic type.
18.8.3.Semantics🔗
  1. The usual arithmetic conversions are applied.
  2. The result of the ** operator is the left operand raised to the power of the right operand.

18.9.Multiplicative Expressions🔗

18.9.1.Syntax🔗
power-expression multiplicative-expression * power-expression multiplicative-expression / power-expression multiplicative-expression % power-expression
18.9.2.Constraints🔗
  1. Both operands must be of a compatible arithmetic type.
  2. In the case of the * operator, if the left operator is a string, the right operand must be an integral.
18.9.3.Semantics🔗
  1. The usual arithmetic conversions are applied.
  2. The result of the * operator, when applied to two arithmetic types, is the left operand multiplied by the right operand.
  3. The result of the * operator, when applies to a string operand and an integral operand, is the value of the string operand with its content repeated an amount of times specified by the integral operand.
  4. The result of the / operator is the left operand divided by the right operand.
  5. The result of the % operator is the remainder of dividing the left operand by the right operand.

18.10.Additive Expressions🔗

18.10.1.Syntax🔗
multiplicative-expression additive-expression + multiplicative-expression additive-expression - multiplicative-expression
18.10.2.Constraints🔗
  1. For the - operator, both operands must be a compatible arithmetic type.
  2. For the + operator, either both operands must be of a compatible arithmetic type, or the left operand must be a string, and the other operand must be a non-void value.
18.10.3.Semantics🔗
  1. The usual arithmetic conversions are applied.
  2. The result of the + operator, when both operands are arithmetic, is the left operand plus the right operand.
  3. The result of the + operator, when the left operand is a string, is the string operand’s string value concatenated with the string representation of the other operand. (See .)
  4. The result of the - operator is the left operand minus the right operand.

18.11.Shift Expressions🔗

18.11.1.Syntax🔗
additive-expression bitshift-expression << additive-expression bitshift-expression >> additive-expression
18.11.2.Constraints🔗
  1. Both operands must be of an integral type.
18.11.3.Semantics🔗
  1. The result of the « operator is the value of the left operand with its bits shifted to the left by the value of the right operand.
  2. The result of the » operator is the value of the left operand with its bits shifted to the right by the value of the right operand.
  3. In the case the right operand is a negative value, the operation acts as the inverse operation: left shift becomes right shift and vice versa.

18.12.Relational Expressions🔗

18.12.1.Syntax🔗
bitshift-expression relational-expression < bitshift-expression relational-expression <= bitshift-expression relational-expression > bitshift-expression relational-expression >= bitshift-expression
18.12.2.Constraints🔗
  1. Both operands must be of a compatible comparable type (See .)
18.12.3.Semantics🔗
  1. If both operands are compatible arithmetic types, then the usual arithmetic conversions are applied.
  2. The result of the < operator is a boolean true value if the left operand’s value is less than the right operand’s value.
  3. The result of the <= operator is analogous to the result of the < operator, except that it also returns a boolean true value when the left operand’s value is equal to the right operand’s value.
  4. The result of the > operator is a boolean true value if the left operand’s value is greater than the right operand’s value.
  5. The result of the >= operator is analogous to the result of the > operator, except that it also returns a boolean true value when the left operand’s value is equal to the right operand’s value.

18.13.2.Constraints🔗

18.13.3.Semantics🔗
  1. If both operands are compatible arithmetic types, then the usual arithmetic conversions are applied.
  2. The result of the == operator is a boolean true value if the left operand’s value is equal to the right operand’s value.
  3. The result of the != operator is the inverse of the == operator’s value.

18.14.2.Constraints🔗

18.14.3.Semantics🔗

18.17.Logical AND Expressions🔗

18.17.1.Syntax🔗

18.17.2.Constraints🔗

18.17.3.Semantics🔗

18.18.2.Constraints🔗

18.18.3.Semantics🔗
  1. The usual arithmetic conversions are applied if both operands are arithmetic types.
  2. The result of the || operator is a boolean true value if at least one of the operands are a boolean true value.
  3. If the left operand evaluates to a true value, the right operand must not be evaluated.

18.19.Conditional Expression🔗

18.19.1.Syntax🔗

18.19.2.Constraints🔗
  1. The condition expression must result in a boolean-assignable value.
  2. Both the left and the right operands must result in a compatible type.
18.19.3.Semantics🔗
  1. The condition operand is evaluated first, if it results in a true value, the left operand is the result of the expression, otherwise the right operand is the result.
  2. If the left operand is the result, the right operand must not be evaluated, and vice versa.

  2. For simple assignment operations, the result of an assignment expression is the right operand’s value. As a side effect, the right operand’s value is written to the left operand’s object.

Intermediate Representation (Bytecode Format)

The result of the compilation of a Tetral source file should be a Tetral Bytecode file.

Bytecode files are binary files with little-endian byte ordering.

23.File Header🔗

Each Tetral IR file must be prefixed with a file header to provide information about the file’s contents. The layout of the header shall be as follows.

The header shall begin with an ASCII string that must always have the value TetralLang. This shall be immediately followed by a 16-bit unsigned integer denoting the file’s version.

The file version integer is an incrementing integer which specifies what version of the Tetral bytecode format the file complies with.

The following file versions are valid

Version numberDescription
1The first version of the Tetral Language

The vile version integer must then followed by a repeating pattern. Each instance of this pattern shall begin with a single unsigned byte, the entry type. No entry may be defined twice. Each entry’s presence in the file is optional.

The following types are valid.

23.1.The STRTABLE Entry🔗

This entry shall be comprised of a 64-bit unsigned integer: an offset of the string table’s data from the start of the file, and a 32-bit unsigned integer: the number of entries in the string table.

(See 23.9. String Pool Table)

23.2.The STRDATA Entry🔗

This entry shall be comprised of two 64-bit unsigned integers, the first is an offset and the second is a size. The offset specifies where, from the start of the file, the file’s string pool data is located and the size specifies the size (in bytes) of the file’s string pool data.

(See 23.10. String Pool Data)

23.3.The TYPETABLE Entry🔗

This entry shall be comprised of a 64-bit unsigned integer: an offset of the type table’s data from the start of the file, and a 32-bit unsigned integer: the number of entries in the type table.

(See 23.11. Type Table)

23.4.The FUNCTABLE Entry🔗

This entry shall be comprised of a 64-bit unsigned integer: an offset of the function table’s data from the start of the file, and a 32-bit unsigned integer: the number of entries in the function table.

(See 23.21. Function Table)

23.5.The INSTRBLOCK Entry🔗

This entry shall be comprised of the following pieces of data. The values shall appear in the binary in the order they are defined here.

Instruction block offset
A 64-bit unsigned integer that must specify the file's instruction block offset from the start of the file.
Instruction block size
A 32-bit unsigned integer that must specify the file's instruction block size in bytes.
Instruction count
A 32-bit unsigned integer that must specify how many instructions are in the instruction block.

(See 23.22. Instructions Block)

23.6.The RDATA Entry🔗

This entry shall be comprised of two 64-bit unsigned integers, they are as follows and appear in the order they are listed.

  1. The offset of the data block from the start of the file.
  2. The size of the data block, in bytes.

(See 23.23. Data Block)

23.7.The MDATA Entry🔗

This entry shall be comprised of the following values which and appear in the order they are listed.

The file's global scope size
A 64-bit unsigned integer that shall determine how many bytes are required to represent the variables stored in the file's global scope.
Entrypoint function index

An 32-bit unsigned integer index that shall reference an entry in the function table. This referenced function shall be where execution of this file shall begin.

A value (in hexadecimal) of 0xFFFFFFFF shall mean that the file has no entrypoint and cannot be executed by itself.

23.8.The ADATA Entry🔗

This entry shall begin with a 32-bit unsigned integer that denotes the number of key value pairs stored in the section.

It shall then be followed by a number of key-value pairs of strings. The number of these pairs shall be determined by the prefixing 32-bit unsigned integer. Each string must be prefixed with a 16-bit unsigned integer denoting the length of the string and must then be followed by that many bytes of UTF-8 code units.

23.9.String Pool Table🔗

To be referred to as the String Pool Table, or just the String Table, shall be a list of 32-bit unsigned integer pairs. The number of entries in the table is determined in the STRTABLE entry in the file header.

Each 32-bit unsigned integer in each pair is defined as follows:

String Pool Offset
The first 32-bit unsigned integer must be an address of a string's content in the String Pool Data.
String Length
The second integer must be the number of UTF-8 code units in the string.

The first entry in the list may be a “null” string entry, meaning an entry with offset 0 and length 0, used as a placeholder for an empty, or null, string.

If this section is present in a bytecode file, then the String Pool Data section must be present too, as well as the corresponding entries in the header.

23.10.String Pool Data🔗

This section shall be a block of UTF-8 code units. The size and location of this section shall determined by the STRPOOL entry in the file’s header.

If this section is present in a bytecode file, then the String Pool Table section must be present too, as well as the corresponding entries in the header.

23.11.Type Table🔗

This section shall be a list of type definitions. The number of definitions in this section and the section’s location in the file shall be determined by the TYPETABLE entry in the header.

Each definition must be prefixed with 2 values, an unsigned 32-bit integer and an 8-bit unsigned integer.

The first integer shall be the “type index” of the type definition. This index is used in function table entries, other type table entries, and in some IR instructions to reference the type definition.

The second 8-bit unsigned integer shall mark the type of the entry. The following values are considered valid.

23.12.Array Values Inside Entries🔗

Multiple entries in the type table may define a list or array of which holds some kind of values. An array is a sequential list of data. The terms array and list will be used interchangeably inside the following sections.

All arrays inside type table entries are prefixed with a 16-bit unsigned integer that determines the number of entries in that array or list.

23.13.Arrays, Nullable Definitions and Reference Definitions🔗

These are defined in one section since their schema is identical, but each type results in a different type construct.

These entries shall define only a single 32-bit unsigned integer value. It is the type index of the type they reference.

The referenced type index must not be a null type index.

23.14.Function Signatures🔗

Function signatures shall defined with the following values. The values appear in the binary in the order they are defined here.

Return type index
32-bit unsigned integer index into the type table, referencing the type the function signature uses as a return type. This may not be a null type index.
Variadic state
8-bit unsigned integer that shall have a value of either 0 or 1 used to determine if the function takes in a variable number of arguments.
Parameter list index
A 32-bit unsigned integer referencing the PARAMLIST entry that outlines the type arguments for this type. If the type has no type arguments, this will be a null type index.
Argument types list

An array of 32-bit unsigned type indexes referencing the type of the corresponding function argument's type.

None of these may be null type indices. If the variadic state of the function is set to 1, then the last parameter to appear in this list must reference an entry with the type ARRAY.

23.15.Structs🔗

Structs are defined with the following values. The values appear in the binary in the order they are defined here.

Name index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's name.
Namespace index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's namespace. If the type has no namespace, the referenced entry will be the table's null entry.
Property list

A list of struct properties. Each entry in this list shall contain the following data in the order they are written here.

Property Name
32-bit unsigned integer index referring to the entry in the file's string table that is used as the property's name.
Property Type
32-bit unsigned integer index referring to the type index in the file's type table that shall be the struct property's type.

23.16.Enums🔗

Enumerations shall be defined with the following values. The values appear in the binary in the order they are defined here.

Name index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's name.
Namespace index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's namespace. If the type has no namespace, the referenced entry will be the table's null entry.
Constant list
A list of 32-bit unsigned integers. Each integer in this list shall be a reference to an entry in the file's string table. The ordinal value of each name in this list shall be its index in the list.

23.17.Interfaces🔗

Interfaces are defined with the following values. The values appear in the binary in the order they are defined here.

Name index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's name.
Namespace index
32-bit unsigned integer index referring to the entry in the file's string table that is used as the type's namespace. If the type has no namespace, the referenced entry will be the table's null entry.
Type parameter list index
A 32-bit unsigned integer referencing the PARAMLIST entry that outlines the type arguments for this type. If the type has no type arguments, this will be a null type index.
Extends count
A 32-bit unsigned integer that shall determine how many other interfaces an interface extends.
Extends list

An array of 32-bit unsigned integers that shall list the extended interfaces of an interface. The size of this list shall be determined by the Extends count value.

Each type index in this array must reference a INTERFACE type table entry, and may not be a null type index.

Method count
A 32-bit unsigned integer that shall determine how many methods the interface declares.
Method list

This value shall be an array of 32-bit unsigned integers. The number of entries in this list shall be determined by the Method count value.

Each integer value in this list must be an index into the file's function table, referencing the function that's declared by an interface. No entry in this list may be a null function index.

Bytecode Instructions

The Tetral Bytecode Instruction Set is a simple instruction set with instructions that have pre-defined layouts for their arguments. Which instructions exist, their arguments and their numerical codes are defined in the following sections.

Many instructions operate on registers. A register is a virtual container of memory. The Bytecode Instruction Set uses 32 registers, each 64-bits large.

Register 0 is reserved for the program counter. An index of the current instruction being executed by the execution environment. This register will be referred to as the pcr, or as the program counter register.
