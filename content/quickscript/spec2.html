Introduction

Tetral, from the Greek word for "four," is a scripting language intended to be interpreted to provide a platform-agnostic execution system and which is intended to be executed fast with little checks on the IR past the initial compilation.

Core Principles

Additionally, Tetral is designed with the following 4 core principles in mind, hence the name.

Statically Typed
Types must be specified and known at compile-time to allow for the compiler to optimize as much as possible and to provide easy readability for programmers.
Compiled
Compiled to an intermediate representation (also referred to as a bytecode,) which can be executed on any platform as long as an interpreter exists for the platform.
Interpreted
Interpreted by a native interpreter which performs next to checks on the bytecode and executes it to ensure fast execution speed.
Platform-Agnostic
As long as an interpreter exists, it shouldn't matter how the IR was compiled, it should be possible to execute it.

Other Principles

There are more principles this language was designed around, but they aren't as flashy.

No Memory Interaction
A programmer should never have to care about memory or be able to interact with raw memory.
Explicit Null Control

This idea is that object types, should never be null, unless a null value is explicitly allowed. For example, if a variable is declared of an object type, it should be initialized to a value, rather than null. And you shouldn't be able to assign a null value to a non-null type.

This only goes for object types, primitives are initialized to a zero value, while strings and arrays always null-initialized by default, but null arrays and strings are just treated as having a length of 0.

Reference Counted
No garbage collector, just reference counting of objects. When the reference count of an object reaches 0, it is freed and all its properties, if object types as well, have their reference counters decremented.

Concepts

Source File
A UTF-8 encoded text file that contains Tetral source code.
Bytecode/IR/Intermediate Representation
These terms will be used interchangeably in this document, but they all refer to the compiled representation of Tetral source code.
Program
Either a valid Tetral source file or a Tetral bytecode file that can be executed by the interpreter.
Object Types
A broad term to describe any non-primitive value in Tetral. Object types are always represented with a pointer.
Structs
Object types which hold pre-defined properties of pre-defined types that can be instantiated.
Arrays and Strings

Arrays are objects of a fixed length that contain sequential data of a pre-defined type.

Arrays and strings are, for the most part, the same thing. A string is just an array of UTF-8 encoded bytes.

Primitives
Primitives are integral, floating point and boolean types that are not allocated on the heap. The following are the primitive types recognized by Tetral:
bool or boolean
A single byte value representing either a true (1) or false (0) state.
uint8, uint16, uint32 and uint64
Unsigned integral types, the amount of bits the primitive uses is specified in the name of each one.
int8, int16, int32 and int64
Signed integral types, the amount of bits each uses is specified in the name of each type.
float32 and float64
Floating point types, the amount of bits the primitive uses is specified in the name of each type.
Boolean-like

A value which can in some way be evaluated as true or false.

For bool this is obvious, for primitive types, the value of 0 results in false, while any non-zero value results in true.

For arrays and strings, a null value, (aka that with a length of 0) results in false, while any non-zero length array results in true.

Struct types cannot be assigned to a boolean like value other than in the case of a nullable struct type, where a null value results in false, and anything else results in true.

Language

Tetral files are written in UTF-8 encoded text files, referred to as "source files." They must follow the grammar defined in the following sections.

Comments

Except within a string or character literal, the characters // and # denote the beginning of a line comment. The comment consumes the rest of the source file's line, or until the end of input has been reached.

Except within a string or character literal, the characters /* denote the beginning of a block comment. The comment consumes input until a matching */ sequence has been found, or until the end of input has been reached.

Except within a string or character literal, the characters /** denote the beginning of a documentation comment. The comment consumes input until a matching */ sequence has been found, or until the end of input has been reached.

In almost all cases, comments are simply skipped over and ignored, except for documentation comments (Starting with /**) which are linked to the specific declaration that they prefix.

Cast Expression

Syntax

cast-expression:
value-cast-expression
bit-cast-expression
value-cast-expression:
cast ( type-expression , expression )
bit-cast-expression:
bitcast ( type-expression , expression )

Semantics

  1. Casts a value returned by an expression to a different type.
  2. In the event an integral type is being cast to a floating point type, the integer should be transformed such that the value of the resulting floating point number is equal to the integral number's value.
  3. In the event a floating point type is being cast to an integral type, the floating point value should be transformed such that the value of the resulting integral number is the rounded down value of the floating point number.
  4. In any case other than the two aforementioned ones, the expression need not be handled by the compiler and can be treated as if it doesn't exist.

Constraints

  1. Cast expressions can only cast from one primitive type to another, for example, they can be used cast from a floating point to an integral type.

Coalescence Expression

Syntax

coalescence-expression:

Constraints

  1. It must be possible to resolve the left-hand-side expression to a boolean-like value.
  2. The values of both the left-hand-side expression and the right-hand-side must be of a compatible type.

Semantics

  1. Evaluates the left-hand-side expression, and if it's boolean-like value results in a false value, the right-hand-side is evaluated.

Unary Increment Expressions

Syntax

unary-increment-expression:
++ unary-expression
unary-expression ++

Constraints

  1. The operand must be a valid lvalue that can be modified.
  2. The operand must be of an integral or floating point type.

Semantics

  1. If the increment operator is placed before the operand, the result is the value of the operand incremented by 1. As a side effect, the resulting value is written to the operand object.
  2. If the increment operator is placed after the operand, the result is the value of the operand. As a side effect, the operand's value is incremented by 1 and written to the operand object.

  2. If the decrement operator is placed after the operand, the result is the value of the operand. As a side effect, the operand's value is decremented by 1 and written to the operand object.

Syntax

  1. The operand must be a valid lvalue.
  2. The operand must be of an integral or floating point type.

Semantics

  1. The result of the - operator is the negative of the operand's value, or positive, if the operand's value is already negative. If the operand's type an unsigned type, the resulting type is a signed type of the same size.
  2. The result of the + operator is the value of the operand.

Arithmetic Operations

This section details constraints and semantics when performing arithmetic operations on two arithmetic (numeric) types.

Operand Conversion Constraints

  1. If both operands are integral types of the same size, but their signedness state differs, then the operation is invalid and an explicit cast must be specified.

Operand Conversion Semantics

  1. If one operand is a floating point value, then the other value must be converted to the same floating point value.
  2. If both operands are floating point values, but of different sizes (eg, left operator is a float32, while the right is a float64) then the smaller operand must be converted to the larger operand's type.
  3. If both operands are integral types, then the smaller operand is converted to the larger operand's type.

Power (POW) Expression

Syntax

power-expression
unary-expression
power-expression ** unary-expression

Constraints

  1. Both operands must be of a compatible arithmetic type.

Semantics

  1. The usual arithmetic conversions are applied.
  2. The result of the ** operator is the left operand raised to the power of the right operand.

Multiplicative Expressions

Syntax

multiplicative-expression
power-expression
multiplicative-expression * power-expression
multiplicative-expression / power-expression
multiplicative-expression % power-expression

Constraints

  1. Both operands must be of a compatible arithmetic type.

Semantics

  1. The usual arithmetic conversions are applied.
  2. The result of the * operator is the left operand multiplied by the right operand.
  3. The result of the / operator is the left operand divided by the right operand.
  4. The result of the % operator is the remainder of dividing the left operand by the right operand.

Additive Expressions

Syntax

additive-expression:
multiplicative-expression
additive-expression + multiplicative-expression
additive-expression - multiplicative-expression

Constraints

  1. Both operands must be of a compatible arithmetic type.

Semantics

  1. The usual arithmetic conversions are applied.
  2. The result of the + operator is the left operand plus the right operand.
  3. The result of the - operator is the left operand minus the right operand.

Shift Expressions

Syntax

bitshift-expression:
additive-expression
bitshift-expression << additive-expression
bitshift-expression >> additive-expression

Constraints

  1. Both operands must be of a compatible integral type.

Semantics

  1. The result of the << operator is the value of the left operand with its bits shifted to the left by the value of the right operand.
  2. The result of the >> operator is the value of the left operand with its bits shifted to the right by the value of the right operand.

Relational Expressions

Syntax

relational-expression:
bitshift-expression
relational-expression < bitshift-expression
relational-expression <= bitshift-expression
relational-expression > bitshift-expression
relational-expression >= bitshift-expression

Constraints

  1. Both operands must be of a compatible comparable type (See .)

Semantics

  1. If both operands are compatible arithmetic types, then the usual arithmetic conversions are applied.
  2. The result of the < operator is a boolean true value if the left operand's value is less than the right operand's value.
  3. The result of the <= operator is analogous to the result of the < operator, except that it also returns a boolean true value when the left operand's value is equal to the right operand's value.
  4. The result of the > operator is a boolean true value if the left operand's value is greater than the right operand's value.
  5. The result of the >= operator is analogous to the result of the > operator, except that it also returns a boolean true value when the left operand's value is equal to the right operand's value.

Equality Expressions

Syntax

equality-expression:
relational-expression
equality-expression == relational-expression
equality-expression != relational-expression

Constraints

  1. Both operands must be of a compatible type.

Semantics

  1. If both operands are compatible arithmetic types, then the usual arithmetic conversions are applied.
  2. The result of the == operator is a boolean true value if the left operand's value is equal to the right operand's value.
  3. The result of the != operator is the inverse of the == operator's value.

Comparison And Equality Semantics

  1. Any two arithmetic values can be compared and their equality checked.
  2. Any two array values that have the same comparable component types can be compared.
  3. Any two array values that have the same component types can have their equality checked.
  4. String values can be compared with other string values and their equality can be checked.
  5. Struct values cannot be compared with other struct types, even structs of the same type, but their equality can be checked.
Struct Equality Semantics
  1. If both operands are represented by the same pointer, they are equal.
  2. If either operand is represented by a null pointer, they are not equal.
  3. If any non-object-type property values in the operands are not equal, then the structs are not equal.
  4. For every object-type property in both structs, the appropriate equality semantics apply.
Array Equality Semantics
  1. If both operands are represented by the same pointer, they are equal.
  2. If either operand's pointer is null, the arrays are not equal.
  3. If either operand's length does not equal the other's, the arrays are not equal.
  4. If any contained values in the operands are not equal, the arrays are not equal.
Array Comparison Semantics
  1. If both arrays are represented by the same pointer, neither is greater nor lesser, they are equal.
  2. If the left operand's length is 0, then the right operand is greater.
  3. If the right operand's length is 0, then the left operand is greater.
  4. If all component values in both operands are equal, neither operand is greater or lesser, they are equal.
  5. If the first non-equal value in the left operand is lesser than the equivalent value in the right operand, the right operand is greater.
  6. If the first non-equal value in the left operand is greater than the equivalent value in the right operand, the left operand is greater.

Loop Flow Control Statements

Syntax

control-flow-statement:
continue identifieropt
break identifieropt

Description

Influences the way a loop executes. Continue statements instruct the loop to move on to the next iteration of execution, while break statements cause the loop to be exited early before its condition can evaluate to a false value.

Control Flow statements can be declared with a label. This label is optional, if no label is specified, the statement changes how the immediate loop behaves. If a label is set, then it controls how the referenced loop behaves.

Constraints

  1. Can only be used inside a loop
  2. If a label is specified, the label can only reference a label of a loop the statement is inside.

For Loop Statements

Syntax

for-loop-statement:
for ( variable-declaration ; expression ; expression ) statement-body

Description

Declares a variable and iterates until the 2nd expression, the loop condition evaluates to a false value. After each iteration the third expression is executed as well.

Constraints

  1. The for loop's second expression must result in a value that can be evaluated as a boolean.

Do While Loop Statements

Syntax

do-while-statement:
do block-statement while loop-condition-expression

Description

Evaluates a block of code until the defined loop condition results in a false value. The loop's block will be evaluated at least once until the condition is reached.

Constraints

  1. The loop's condition must result in a value that can be evaluated as a boolean.

Regular While Loop Statements

Syntax

while-statement:
while loop-condition-expression block-statement

Description

Evaluates a block of code until the defined loop condition results in a false value. If the condition results in a false value when the loop is first reached, the loop's block is not evaluated at all.

Constraints

  1. The loop's condition must result in a value that can be evaluated as a boolean.

Return Statements

Syntax

return-statement:
return expressionopt

Description

Causes the current function to halt execution and return to the caller.

Constraints

  1. Can only be used inside a function body.
  2. If the return statement is used in a non-void function, it must always return a value.
  3. If the return statement is used in a void function, it must never return a value.
  4. The value returned by a return statement, must be assignable to the function's return type.

Assert Statements

Syntax

assert-statement:
assert expression
assert expression : expression

Description

The assert statement evaluates an expression and if expression results in a false value, it throws an error with a potentially user-specified error message.

Constraints

  1. The expression the assert statement evaluates must always result in a Boolean value.
  2. The message expression, if present, must always result in a String value.

Examples

assert true // Does nothing
assert false // Assertion failed!
assert false : "message" // Assertion failed: message
